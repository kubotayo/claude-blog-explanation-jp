1. 処理概要

処理トリガー実行環境制限
定期バッチVercel Cron（毎日 6:00 JST）Vercel Serverless Function実行時間 60秒（Hobby プラン）
初回遡及取得手動（node scripts/seed.mjs）ローカル環境なし（2秒インターバルで全件処理）
定期バッチは1日に公開される記事数が通常1〜5件であるため、60秒以内に完了する見込み。万一タイムアウトが発生した場合は次回バッチで未処理分を再試行する設計とする。

2. クロール処理（crawler.ts）

2-1. 処理フロー

1
ブログ一覧ページを取得
https://claude.com/blog/ に GET リクエストを送り HTML を取得。ページネーションが存在する場合は全ページを順次取得する。
2
記事URLリストを抽出
cheerio で HTML をパースし、各記事へのリンク URL を配列として取得する。
3
未処理URLを特定
Firestore の crawl_log コレクションから処理済み URL を取得し、差分（新規 URL）を抽出する。
4
記事本文を取得
各未処理 URL に GET リクエストを送り、記事の本文・タイトル・著者・公開日・カテゴリを DOM パースで抽出する。

2-2. HTML パース対象フィールド

フィールド取得元（CSS セレクタ候補）必須
タイトルh1, meta[property="og:title"]必須
本文記事本文を含む article または main 要素必須
著者著者名を含む要素（実装時に確認）任意
公開日time[datetime], meta[property="article:published_time"]任意
カテゴリカテゴリラベル要素（実装時に確認）任意
CSS セレクタは実装時に claude.com/blog の実際の HTML 構造を確認して決定する。構造変更時はここを更新すること。

3. 生成処理（generator.ts）

3-1. 処理フロー

1
Claude API 呼び出し
記事本文・タイトル・著者・カテゴリをプロンプトに組み込み、翻訳・解説・スコアリングを1リクエストで依頼する。
2
JSON レスポンスをパース
Claude API のレスポンスから JSON 部分を抽出し、GeneratedArticle 型にバリデーションする。パース失敗時はエラーとして記録する。
3
Firestore に保存
バリデーション済みのデータを articles コレクションに保存し、crawl_log に処理済みとして記録する。

3-2. API 呼び出し設定

パラメータ値理由
modelclaude-opus-4-7翻訳・解説の品質を最大化するため最上位モデルを使用
max_tokens8000詳細解説と全フィールドの出力を収めるため
thinking{ type: "adaptive" }対象読者判定・重要度スコアリングの精度向上のため

4. プロンプト設計

4-1. システムプロンプト

System Prompt
あなたは Anthropic 公式ブログの日本語解説ライターです。
英語の技術ブログ記事を読み、以下の役割を果たしてください。

## あなたの役割
- 翻訳者ではなく「技術ライター」として、原文の内容を深く理解した上で日本語で解説する
- 読者が「誰向けの記事か」「どのくらい重要か」を一目で判断できるメタ情報を付与する
- 原文の情報量を削らず、背景知識や日本市場への示唆を加えて 1.5〜2 倍の情報密度を目指す

## 文体・スタイルルール
- 文体は「です・ます調」で統一する
- モデル名・製品名・API 名は英語のままにする（例: Claude Opus, Function Calling）
- 技術用語は初出時に補足説明を付ける
- 機械翻訳的な直訳は避け、自然な日本語で意訳・補完を積極的に行う

## 出力形式
必ず以下の JSON スキーマに従って出力すること。
JSON 以外のテキストは出力しないこと。

4-2. ユーザープロンプト

User Prompt テンプレート
以下の Anthropic 公式ブログ記事を翻訳・解説してください。

# 原文メタ情報
- タイトル（英語）: {originalTitle}
- 著者: {author}
- カテゴリ: {category}
- 公開日: {publishedAt}
- URL: {originalUrl}

# 原文本文
{originalContent}

# 出力 JSON スキーマ
{
  "japaneseTitle": "日本語タイトル（意訳可）",
  "summary": "3〜5行の要約。この記事が何について、なぜ重要かを端的に伝える",
  "detailedExplanation": "原文の見出し構造を維持した詳細解説（Markdown形式）。各セクションに解説者コメントを追記すること",
  "keyPointsEngineer": ["エンジニア向けポイント1", "ポイント2", "（5〜8項目）"],
  "keyPointsBusiness": ["ビジネス向けポイント1", "ポイント2", "（5〜8項目）"],
  "japanUseCases": "日本での活用イメージ（Markdown形式）。日本のユースケースや文化的文脈を踏まえた実装・活用例",
  "targetAudience": ["engineer", "business", "general", "researcher のうち該当するもの（複数可）"],
  "importanceScore": "S, A, B, C のいずれか",
  "importanceReason": "重要度判定の根拠（1〜2文）"
}

# 重要度スコアの基準
- S: 新モデルリリース・API breaking change など即時対応が必要なもの
- A: 業界インパクトが高い発表・重要な安全性研究
- B: 有用な活用事例・技術解説・機能改善
- C: 一般情報・トピック記事・コミュニティ向け

# 対象読者の基準
- engineer: コード・API・アーキテクチャの話題が中心
- business: ROI・企業導入事例・ワークフロー効率化が中心
- general: Claude の機能紹介・使い方・社会的トピック
- researcher: 論文・モデルの仕組み・安全性研究が中心

4-3. 出力 JSON の型定義

// src/types/article.ts

export type TargetAudience = "engineer" | "business" | "general" | "researcher";
export type ImportanceScore = "S" | "A" | "B" | "C";

/** Claude API が生成するデータ */
export type GeneratedArticle = {
  japaneseTitle: string;
  summary: string;
  detailedExplanation: string;   // Markdown
  keyPointsEngineer: string[];
  keyPointsBusiness: string[];
  japanUseCases: string;         // Markdown
  targetAudience: TargetAudience[];
  importanceScore: ImportanceScore;
  importanceReason: string;
};

/** クロールで取得する原文メタ情報 */
export type CrawledArticle = {
  originalUrl: string;
  originalTitle: string;
  originalContent: string;
  author: string;
  category: string;
  originalPublishedAt: Date | null;
};

/** Firestore に保存する完全な記事データ */
export type Article = GeneratedArticle & CrawledArticle & {
  status: "published" | "error";
  createdAt: Date;
};

5. エラーハンドリング

5-1. エラー種別と対応

エラー種別発生箇所対応
クロール失敗（ネットワークエラー等）crawler.ts最大3回リトライ（指数バックオフ: 1秒 → 2秒 → 4秒）。3回失敗で crawl_log に error を記録し次回バッチで再試行
HTML パース失敗（構造変更等）crawler.tsエラーログを記録して該当 URL をスキップ。アラートとして Firestore に記録
Claude API レート制限（429）generator.ts429 受信時は60秒待機後にリトライ（最大2回）
Claude API 応答の JSON パース失敗generator.tsエラーログを記録して該当 URL をスキップ。次回バッチで再試行
Firestore 書き込み失敗firestore.ts最大3回リトライ後、エラーログを記録
Vercel Cron タイムアウト（60秒超）API Route処理途中で終了しても crawl_log の未記録 URL は次回バッチで再試行される

5-2. crawl_log のエラーレコード

// エラー時に Firestore に記録するデータ
{
  url: "https://claude.com/blog/...",
  status: "error",
  errorMessage: "Failed to parse HTML: selector .article-body not found",
  retryCount: 3,
  crawledAt: Timestamp
}

6. 初回遡及取得スクリプト（scripts/seed.mjs）

6-1. 概要

Vercel Cron の60秒制限を回避するため、初回の全件取得はローカル環境から node scripts/seed.mjs で実行する。処理済み URL は Firestore の crawl_log に記録されるため、途中で中断しても再実行時に未処理分から再開できる。

6-2. 実行方法

# 環境変数を設定してから実行
ANTHROPIC_API_KEY=your_key \
FIREBASE_PROJECT_ID=your_project_id \
node scripts/seed.mjs

6-3. 処理フロー

scripts/seed.mjs
  │
  ├─ 1. claude.com/blog の全ページをクロールして記事URLを全件取得
  │
  ├─ 2. Firestore の crawl_log から処理済みURLを取得
  │
  ├─ 3. 未処理URLを抽出（途中再開対応）
  │
  └─ 4. 各未処理URLに対して順次処理（2秒インターバル）:
        a. 記事本文を取得
        b. Claude API で生成（1記事あたり約10〜30秒）
        c. Firestore に保存
        d. 進捗をコンソールに出力（例: "[5/120] 処理中: ..."）

6-4. 所要時間の見積もり

件数1件あたり所要時間インターバル合計時間
100件約 20秒（Claude API）2秒約 37分
150件約 20秒2秒約 55分
初回遡及取得は1回限りの作業。Claude API の費用は約 $50（100件の場合）で、これは初回のみの一時費用。
