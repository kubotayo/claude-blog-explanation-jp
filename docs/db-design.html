1. 概要

Firebase Firestore（NoSQL ドキュメントDB）を使用する。コレクションは articles（公開記事）と crawl_log（クロール管理）の2つ。

コレクション用途想定ドキュメント数読み書き
articles翻訳・解説済みの公開記事データ100〜500件（積み上がり）読み: Web 表示時 / 書き: バッチのみ
crawl_logクロール済みURLの管理・重複防止articles と同件数読み書き: バッチのみ

2. articles コレクション

articles/{articleId} 翻訳・解説済みの記事データ。ドキュメントIDは Firestore が自動生成する。
フィールド名型必須説明
originalUrl string 必須 原文URL（例: https://claude.com/blog/claude-4）。クロール時の重複チェックには使わず crawl_log を使用する
originalTitle string 必須 原文タイトル（英語）
author string 任意 著者名。取得できない場合は "Anthropic Team"
category string 任意 原文カテゴリ。取得できない場合は空文字
originalPublishedAt timestamp | null 任意 原文の公開日時。取得できない場合は null
japaneseTitle string 必須 Claude API が生成した日本語タイトル
summary string 必須 3〜5行の要約（プレーンテキスト）
detailedExplanation string 必須 詳細解説（Markdown 形式）。フロントエンドで react-markdown でレンダリング
keyPointsEngineer string[] 必須 エンジニア向けポイントの配列（5〜8項目）
keyPointsBusiness string[] 必須 ビジネス向けポイントの配列（5〜8項目）
japanUseCases string 必須 日本での活用イメージ（Markdown 形式）
targetAudience string[] 必須 "engineer" | "business" | "general" | "researcher" の組み合わせ（1〜複数）
importanceScore string 必須 "S" | "A" | "B" | "C" のいずれか
importanceReason string 必須 重要度判定の根拠（1〜2文）
status string 必須 "published" | "error"。生成成功時は "published"、失敗時は "error"
createdAt timestamp 必須 Firestore に保存した日時（serverTimestamp()）
detailedExplanation と japanUseCases は長文（数千文字）になる場合がある。Firestore の1ドキュメントサイズ上限は 1MB であり、通常の記事では問題ないが、極端に長い原文の場合は注意が必要。

3. crawl_log コレクション

crawl_log/{docId} クロール済みURLを管理し重複処理を防ぐ。ドキュメントIDは URL を Base64 エンコードしたものを使用する（URL をそのままIDにすると / が含まれ階層になるため）。
フィールド名型必須説明
url string 必須 クロール済み記事URL
articleId string | null 任意 生成された articles ドキュメントID。エラー時は null
status string 必須 "success" | "error"
errorMessage string | null 任意 エラー時のメッセージ。成功時は null
retryCount number 必須 リトライ回数（初回成功は 0）
crawledAt timestamp 必須 クロール実行日時（serverTimestamp()）

ドキュメントIDの生成方法

// URL を Base64 エンコードしてドキュメントIDとして使用する
// Firestore のIDに使えない文字（/ 等）を回避するため
function urlToDocId(url: string): string {
  return Buffer.from(url).toString("base64url");
}

4. インデックス設計

4-1. 複合インデックス

コレクションフィールド1フィールド2用途
articles status ASC importanceScore ASC 公開記事を重要度順に取得（一覧ページ・フィルター）
articles status ASC createdAt DESC 公開記事を新着順に取得（将来の新着順ソート用）
Firestore は配列フィールド（targetAudience）に対して array-contains クエリを使用できる。対象読者フィルターは where("targetAudience", "array-contains", "engineer") で実装する。ただし array-contains と他の複合クエリを組み合わせる場合は追加インデックスが必要になる場合がある。

4-2. 単一フィールドインデックス（自動作成）

Firestore は各フィールドに対して自動的に単一フィールドインデックスを作成する。以下のクエリは追加設定なしで動作する。

  • where("status", "==", "published")
  • where("importanceScore", "==", "S")
  • where("targetAudience", "array-contains", "engineer")
  • orderBy("createdAt", "desc")

5. セキュリティルール

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // articles コレクション
    // 読み取り: 全公開（認証不要）
    // 書き込み: 禁止（サーバーサイドの API Routes からのみ書き込む）
    match /articles/{articleId} {
      allow read: if true;
      allow write: if false;
    }

    // crawl_log コレクション
    // 読み書き: 禁止（サーバーサイドの API Routes からのみアクセス）
    match /crawl_log/{logId} {
      allow read, write: if false;
    }
  }
}
クライアントからの直接書き込みを allow write: if false で禁止している。サーバーサイド（Next.js API Routes）からは Firebase Client SDK がサーバー上で動くため、セキュリティルールが適用される点に注意。将来的に Admin SDK に移行する場合はセキュリティルールはバイパスされるため、この点を考慮すること。
