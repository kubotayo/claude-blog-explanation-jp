1. プロジェクト概要

https://claude.com/blog/ に投稿されている Anthropic の公式ブログ記事を自動で取得し、Claude API を使って日本語に翻訳・解説した記事を自社 Web サイトに公開するシステム。

読者が記事を見たときに 「内容の詳細」「誰向けか」「どのくらい重要か」 が一目でわかる記事フォーマットを提供することを最重要要件とする。

ゴール

  • Anthropic の最新情報を日本語で素早くキャッチアップできる場を提供する
  • 翻訳だけでなく「解説」として付加価値を加え、日本市場での活用イメージを示す
  • バッチ処理により人手を最小化し、継続的な自動更新を実現する

2. 記事フォーマット仕様

生成される各記事は以下の構成を持つ。このフォーマットが本システムの最重要成果物である。

重要度 S エンジニア向け ビジネス向け 2026-05-20 ／ Anthropic Team

Claude 4 発表：新モデルの性能と API 変更点を詳解

【要約】 Anthropic が Claude 4 シリーズを発表。Opus・Sonnet・Haiku の3モデルが同時リリースされ、コーディング・推論能力が大幅に向上。API の breaking changes に注意が必要。

  • エンジニア向けポイント：API 変更点、移行手順
  • ビジネス向けポイント：コスト感、活用シナリオ
  • 日本での活用イメージ：国内事例・日本語性能

2-1. 記事の構成要素

要素内容必須
メタヘッダー重要度スコア・対象読者ラベル・原文タイトル・公開日・著者・カテゴリ・原文URL必須
日本語タイトル原文を意訳した読みやすい日本語タイトル必須
要約3〜5行のエレベーターピッチ。「何について」「なぜ重要か」を端的に伝える必須
詳細解説原文の見出し構造を維持した日本語訳 + 各セクションへの解説者コメント（背景知識・日本市場への示唆）必須
ポイントまとめ対象読者別（エンジニア／ビジネス）の箇条書き、5〜8項目必須
日本での活用イメージ日本のユースケース・文化的文脈を踏まえた実装・活用例必須
関連記事リンク同カテゴリの過去記事へのリンク任意

2-2. 重要度スコア（S / A / B / C）

Claude API が以下の評価軸をもとに S〜C の4段階で判定する。

スコア基準例
S新モデル・新機能リリース、API breaking change など即時対応が必要Claude 4 発表、Function Calling 変更
A業界インパクトが高い発表、重要な安全性研究新しい料金体系、企業向け機能追加
B有用な活用事例・技術解説・機能改善Prompt Engineering tips、事例紹介
C一般情報・トピック記事・コミュニティ向けカルチャー・採用・イベント告知

スコアリングの評価軸：新機能・発表の有無 ／ 業界インパクト ／ 日本市場関連度 ／ 技術的深度

2-3. 対象読者ラベル

Claude API が記事本文を分析し、以下のラベルを1つ以上付与する（複数可）。

ラベル判定基準
エンジニア向けコード・API・アーキテクチャの話題が中心
ビジネス向けROI・企業導入事例・ワークフロー効率化が中心
一般向けClaude の機能紹介・使い方・社会的トピック
研究者向け論文・モデルの仕組み・安全性研究が中心

3. 機能要件

3-1. クローリング・記事取得

項目仕様
取得対象URLhttps://claude.com/blog/ および各記事ページ
取得フィールドタイトル・本文・著者・公開日・カテゴリ
初回実行全件遡及取得（100件超を想定）
定期実行前回取得済みURLとの差分を比較し、新規記事のみ処理対象とする
重複チェック取得済み記事URLを Firestore に保存し、同一URLは再処理しない
エラー時最大3回リトライ後、エラーログを Firestore に保存して次回バッチで再試行

3-2. 翻訳・解説生成

項目仕様
利用APIClaude API（Anthropic）
モデルclaude-opus-4-7（高品質・文脈理解が必要なため）
出力形式Markdown → Firestore に保存し、フロントエンドでレンダリング
同時生成翻訳・解説・対象読者判定・重要度スコアリングを1リクエストで生成
処理間隔初回遡及時は1記事ごとに2秒インターバルを設けAPIレート制限を回避

3-3. Web 表示

機能仕様
記事一覧重要度・対象読者ラベルを一覧で表示。重要度順（S→C）でデフォルトソート
フィルター重要度（S/A/B/C）・対象読者でフィルタリング
記事詳細セクション2で定義したフォーマットで表示
原文リンク各記事に原文URLへのリンクを表示
キャッシュISR（revalidate: 3600 秒）で静的配信しつつ新着を反映

3-4. バッチ処理フロー

1. Vercel Cron が毎日 6:00 JST に /api/cron/crawl を呼び出す
2. claude.com/blog/ をクロールして記事URLリストを取得
3. Firestore の crawl_log と照合し、未処理URLを抽出
4. 各未処理記事に対して:
   a. 記事本文を取得
   b. Claude API に翻訳・解説・メタ情報生成を依頼
   c. 結果を Firestore の articles コレクションに保存
   d. crawl_log に処理済みとして記録
5. 完了ログを Firestore に記録

4. データモデル（Firestore）

4-1. articles コレクション

フィールド型説明

authorstring著者名
categorystring原文カテゴリ

5. 非機能要件

項目仕様
バッチスケジュール毎日 6:00 JST（Vercel Cron）
承認フローなし（生成後に自動公開）
遡及取得全件（初回のみ、過去記事100件超を想定）
公開範囲全公開
文体です・ます調統一
固有名詞モデル名・製品名・APIは英語のまま（例: Claude Opus, Function Calling）
翻訳品質元記事の情報量を削らず、解説を加えて1.5〜2倍の情報密度を目標
エラー通知バッチ失敗時は Firestore にエラーログを記録
Vercel CronHobby プランの場合1日1回の制約あり（Pro プランへの変更を検討）

6. 技術スタック

レイヤー技術用途
フロントエンドNext.js (App Router) + TypeScript + Tailwind CSS記事一覧・詳細ページ
バッチ処理Next.js API Routes + Vercel Cron Functionsクロール・翻訳・Firestore 書き込み
AIClaude API (claude-opus-4-7)翻訳・解説生成・メタ情報判定
データベースFirebase Firestore記事データ・クロールログ保存
ホスティングVercelフロントエンド・API Routes のデプロイ
クローリングNode.js fetch + cheerioHTML 取得・DOM パース
Markdown レンダリングreact-markdown + remark-gfm記事本文の表示
注意: Vercel Hobby プランでは Cron Functions は1日1回・実行時間60秒の制限がある。初回の遡及取得（100件超）では時間が不足する可能性があるため、初回のみローカルから手動実行するスクリプトを別途用意する。

7. コスト試算

処理想定トークン数（入出力合計）月間処理件数月額試算
翻訳・解説・メタ情報生成（claude-opus-4-7）約 10,000 tokens/件30〜60 件約 $15〜$30
初回遡及処理（一時費用）約 10,000 tokens/件100 件約 $50（初回のみ）
Vercel（Hobby プラン）——無料
Firebase（Spark プラン）——無料〜低コスト
定常月額合計約 $15〜$30

8. スコープ外（将来検討）

  • 承認フロー・管理画面（自動公開のため初版では不要）
  • SNS 自動投稿（X / LinkedIn など）
  • 全文検索機能
  • 記事の更新検知（既存記事が編集された場合の再翻訳）
  • Zenn / note へのクロスポスト
  • 多言語対応（日本語のみ）
